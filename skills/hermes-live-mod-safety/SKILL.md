# Hermes Live Mod & Code Safety

Используй этот скилл при внесении любых изменений в рантайм-код Hermes, создании или обновлении декларативных модов (`~/.hermes/mods/`), управлении зависимостями, корректировке доставки сообщений в Telegram, поведении шлюза и обслуживании супервизируемых сервисов.

## Регламент безопасной модификации (Safety Procedure)

1. **Анализ контекста:** Перед проектированием изменений изучи актуальный живой код ядра (`/usr/local/lib/hermes-agent`), тесты, реестр активных модов (`~/.hermes/mods/`), граф зависимостей и профильные скиллы.
2. **Отказ от ручных бэкапов и cron-скриптов:** Больше не требуется вручную копировать файлы ядра в резервные каталоги или настраивать cron-задачи отката. Используй нативные дельта-снапшоты движка v1.5.0: `python3 ~/.hermes/mods/runner.py snapshot restore` (сохраняет точные SHA-256 хэши и восстанавливает измененные файлы ядра мгновенно и атомарно).
3. **Автоматический сторож шлюза (Watchdog):** При применении любых модов, затрагивающих ядро или шлюз, всегда запускай наложение со встроенным 30-секундным сторожем:
   ```bash
   python3 ~/.hermes/mods/runner.py apply <mod_id> --watchdog --watchdog-window 30
   ```
   Если шлюз (`hermes-gateway.service`) в течение 30 секунд упадет, завершится с ошибкой или сменит PID (петля перезапусков), сторож автоматически выполнит мгновенный откат к предпусковому снапшоту ядра.
4. **СТРОЖАЙШИЙ ЗАПРЕТ рестартов шлюза:** КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО выполнять `systemctl restart hermes-gateway`, `systemctl reload`, `hermes gateway restart` и любые другие перезапуски шлюза или сервисов! Супервизоры и сторонние cron-скрипты могут превратить перезапуск в цикл отказов. Все изменения применяются на лету, а ядро считывает плоские JSON-кэши по `mtime` без простоя.
5. **Проверка окружения и зависимостей:** Проверяй активный виртуальный venv Hermes на наличие каждой новой зависимости. Тестируй точный импорт установленного API и версию; метаданных пакета или wheel-файла недостаточно.
6. **Изолированное тестирование:** Проверяй мод в изолированном контексте. Запускай проверку синтаксиса, импорты, точечные тесты поведения и валидацию `python3 ~/.hermes/mods/runner.py test <mod_id> --no-cache`. Тестируй каждый затрагиваемый путь доставки, а не только простейший сценарий.
7. **Сверка с базовым состоянием (Baseline Reconciliation):** Перед редактированием или созданием мода сравнивай живой целевой файл с `git diff -- <file>` и восстанавливай чистый базовый файл через `git show HEAD:<file>`. Никогда не откатывай весь репозиторий целиком и не затирай существующие рабочие правки. Воспроизводи в памяти наложение модов на чистый базовый файл, чтобы отличать намеренно модифицированное состояние от непримененного. Минимизируй размер заменяемых блоков. Запускай `python3 ~/.hermes/mods/runner.py apply` дважды: первый раз — `applied` с успешной верификацией, второй раз — `already_applied` с `verified: true`.
8. **Версионирование и папочные скиллы:** После создания или обновления мода всегда повышай его версию (`version: x.y.z`) в манифесте. Перед наложением валидируй декларации через `python3 ~/.hermes/mods/runner.py verify`. В YAML-патчах всегда используй литеральный блочный скаляр `|`, чтобы не требовалось экранирование кавычек, докстрингов и обратных слэшей в регулярных выражениях. Не считай успешную запись файла подтверждением наложения мода. Папочные моды могут нести собственные скиллы в `skills/<skill_name>/SKILL.md`: при `enabled: true` они автоматически регистрируются в `skills_list`, `skill_view` и системном промпте Hermes, а при `enabled: false` изолируются. Локальные пользовательские скиллы (`~/.hermes/skills/`) имеют приоритет над скиллами модов. Синхронизируй изменения модов и скиллов в `~/workspaces/hermes-mods/` и `~/Hermes-memory`.
9. **Защита цикла рассуждений и предотвращение утечек (Thinking Leaks):** При модификации цикла агента или финального ответа на шаге гарантируй подавление продвижения reasoning (`reasoning promotion`), если `tool_results_this_turn > 0`. Пустой контент после вызова инструментов — это прерывание/остановка по пустому ответу (`empty-response choke`), а не завершенный ответ; он обязан направляться в механизм восстановления `_EMPTY_TOOL_RESPONSE_NUDGE` для обработки результатов вызова инструментов, а не утекать в виде монолога планирования в чат. Категорически запрещено хардкодить хрупкие эвристики ключевых слов/регулярных выражений (например, классифицировать монологи рассуждений по открытым словарям на 1-м шаге) для отлова thinking leaks: ложные срабатывания на реальных кратких ответах строго недопустимы для пользователя, который предпочитает вручную повторить шаг, чем терять легитимные ответы. Опирайся исключительно на структурные рантайм-инварианты (`tool_results_this_turn > 0`), а не на спекулятивный анализ текста.
10. **Контроль завершения и дельта-снапшоты:** Считай работу завершенной только после прохождения как изолированных, так и сквозных рантайм-проверок. Если верификация не пройдена или возникла нестабильность, немедленно выполни `python3 ~/.hermes/mods/runner.py snapshot restore` для возврата ядра к предпусковому состоянию и сообщи о проблеме.

## Доставка и форматирование сообщений (Delivery & Formatting)

Для изменений в интеграции Telegram тестируй отправку обычных сообщений, финальное стриминговое редактирование, разделение переполняющихся сообщений (overflow continuations), резервную доставку (fallback), сервисные/статусные сообщения и подписи к медиа. Исправление форматтера, работающее только для финального ответа агента, считается неполным.

При разбиении сообщений, содержащих раскрывающиеся цитаты (expandable blockquotes `**> ... ||`):
- Усечение на границе чанка оставляет чанк 1 с открывающим `**>` без закрывающего `||` (Telegram деградирует его до обычной цитаты), а чанк 2 — с висячим `||` без открывающего `**>`.
- При чанкинге в MarkdownV2 функция `_repair_split_chunk_blockquotes` обязана балансировать оба чанка: чанк 1 должен закрываться `||` (суффиксы пагинации, например `(1/2)`, размещаются внутри или перед `||`), а чанк 2 должен заново открываться `**>` на продолжении строки цитаты.
- При доставке entities через Bot API (`_telegram_entity_payload`) функция `split_entities` делит текст по смещению символов с нативным сохранением `MessageEntity(type='expandable_blockquote')` через границы чанков. Убедись, что методы `send` (`_send_text_locked`), редактирование переполнения (`_edit_overflow_split`) и продолжение переполнения (`_send_overflow_continuation`) доставляют entities, а не деградируют в сырой текст или обрезку MarkdownV2.
- Кастомные раскрывающиеся цитаты (`**> ... ||`) должны отслеживаться при нормализации и явно повышаться до `expandable_blockquote`, так как библиотеки рендеринга (например, `telegramify-markdown`) по умолчанию повышают только цитаты, превышающие порог длины (>200 символов), оставляя короткие цитаты обычными.
- В эвристике детекции entities (`_telegram_plain_candidate`) ВСЕГДА сначала проверяй явные конструкции Markdown (`**`, `||`, блоки кода, ссылки, списки, заголовки, цитаты) ДО классификации сообщения как plain-text по ведущим статусным эмодзи (`🎙️`, `✅`, `❌`, `⚠️`) или открывающим скобкам (`[`, `{`). Безусловное определение статусных префиксов как простого текста превращает валидный Markdown (например, транскрипции STT `🎙️ provider\n**> text||`) в сырой неразобранный текст с пустыми сущностями.
- При форматировании статусов слэш-команд (например, `/agents`) скрывай внутренние UUID/хэши (префиксы `deleg_...`) и отображай понятные человеку якоря (например, копируемые метки топиков `топик #<thread_id>`).

Предпочитай сборку единого финального пейлоада перед разбиением. При использовании Telegram entities формируй все префиксы, статус и тело целиком, и только потом конвертируй в сущности, иначе смещения сдвинутся. Всегда рассчитывай длину в UTF-16, так как эмодзи и спецсимволы занимают по две единицы UTF-16. Разделяй plain/system текст и Markdown-ввод, валидируй реальные объекты сущностей `python-telegram-bot` и параметры методов.

Удаляй маркеры пагинации только тогда, когда продукт этого явно не требует; это предотвращает противоречивые суммы в промежуточных снапшотах, но само по себе не делает границы Markdown безопасными.

## Верификационные ворота (Verification Gates)

- Изолированная копия компилируется и успешно импортируется.
- Точный API зависимостей работоспособен в активном рантайме.
- Длинный текст разбивается без усечений и дублирования доставки.
- Форматирование сохраняется на границах чанков для кода, ссылок, цитат, акцентов, спойлеров и эмодзи.
- Все затронутые пути используют одну и ту же проверенную структуру данных.
- Наложение мода идемпотентно (`runner.py apply` возвращает `already_applied` и `verified: true`).
- Перезапуск шлюза или сервисов не выполняется (Zero Downtime Policy).
- Автоматический сторож подтверждает стабильность шлюза (`--watchdog`).

## Разграничение конфигурации: Ядро vs Параметры модов

### 1. Конфигурация ядра Hermes (`hermes config set`)
- Прямое редактирование или патчинг `~/.hermes/config.yaml` блокируется внутренними механизмами безопасности от мутации файлов.
- Для обновления конфигурации ядра всегда используй нативный CLI-интерфейс Hermes:
  ```bash
  hermes config set <key> '<value>'
  # Пример:
  hermes config set providers.gpt.models '{"model_id": { ... }}'
  ```

### 2. Конфигурация параметров и секретов модов (`runner.py config`)
- Конфигурация модов изолирована от системных настроек ядра и управляется через движок:
  ```bash
  # Просмотр параметров и статуса конфигурации мода
  python3 ~/.hermes/mods/runner.py config <mod_id>

  # Установка публичного параметра (сохраняется в ~/.hermes/config.yaml в секции mods.<mod_id>.<key>)
  python3 ~/.hermes/mods/runner.py config <mod_id> --set <key>=<value>

  # Установка конфиденциального секрета (сохраняется СТРОГО в ~/.hermes/secrets.yaml с правами 0600)
  python3 ~/.hermes/mods/runner.py config <mod_id> --set-secret <key>=<value>

  # Автоматическое заполнение дефолтных значений из манифеста
  python3 ~/.hermes/mods/runner.py config <mod_id> --populate
  ```

## Запрещенные действия (Do not)

- Запрещено модифицировать живые файлы ядра без предварительного изолированного тестирования.
- Запрещено выполнять `systemctl restart hermes-gateway`, `systemctl reload`, `hermes gateway restart` или любые другие перезапуски сервисов.
- Запрещено настраивать ручные cron-откаты или самодельные скрипты бэкапов вместо нативных `runner.py snapshot` и `--watchdog`.
- Запрещено писать секреты модов в открытые файлы конфигурации вместо `secrets.yaml` (`0600`).
- Запрещено считать успешным решение на основании одних лишь синтаксических проверок без проверки рантайма.
- КАТЕГОРИЧЕСКИ НЕ ПЕРЕНОСИТЬ системные скиллы управления модами (`hermes-mods-management` и `hermes-live-mod-safety`) в директории модов! Они обязаны жить в `~/.hermes/skills/devops/`, чтобы агент не терял представление об устройстве модов при сбоях или обновлении движка.
