# Hermes Mod Safety & Third-Party Audit

Используй этот скилл для аудита безопасности сторонних модов (скачанных из репозиториев GitHub, внешних архивов или предложенных пользователем) перед их установкой в экосистему Hermes Agent.

Главная цель — гарантировать, что сторонний код не нарушит изоляцию песочницы, не совершит побег из кодовой базы ядра, не скомпрометирует токены и не нарушит работу пула уже активных системных и кастомных модов.

---

## Векторы угроз при установке сторонних модов

1. **Path Traversal (выход за пределы песочницы):** Попытка декларативного патча перезаписать системные файлы ОС (`/etc/passwd`, `/etc/cron.*`, `~/.ssh/authorized_keys`, `~/.bashrc`).
2. **Деструктивный или вредоносный код в скриптах:** Вызовы команд с удалением файлов (`rm -rf`), криптомайнеры, скрытый запуск сетевых шеллов (`reverse shell`), скачивание непроверенных бинарников (`curl ... | bash`).
3. **Кража чувствительных данных:** Чтение токенов из `~/.hermes/secrets.yaml`, `.env`, ключей SSH или экспорт переменных окружения на сторонние серверы.
4. **Коллизии и нарушение целостности:** Конфликты патчей с уже установленными модами, переопределение существующих слэш-команд, циклические блокировки или поломка базового цикла агента.

---

## 1. Защита от Path Traversal

Все цели патчей обязаны указывать строго на файлы внутри корня Hermes:
`HERMES_ROOT = Path("/usr/local/lib/hermes-agent")`

### Правила проверки путей:
- **Запрет абсолютных путей:** Поле `file:` в `targets` категорически не должно начинаться с `/` (например, `/etc/shadow` или `~/.bashrc`).
- **Запрет выхода наверх через `..`:** Пути вроде `../../etc/passwd` или `hermes_cli/../../.ssh/id_rsa` блокируются.
- **Проверка через `is_relative_to`:**
  ```python
  from pathlib import Path
  hermes_root = Path("/usr/local/lib/hermes-agent").resolve()
  target_path = (hermes_root / target_file).resolve()
  if not target_path.is_relative_to(hermes_root):
      raise SecurityError(f"Path Traversal detected: {target_file}")
  ```
- **Символические ссылки (Symlink Attacks):** Проверяй, чтобы файлы в каталоге мода (`targets`, `scripts`, `skills`) не являлись симлинками, указывающими на внешние критические файлы хоста.

## 2. Статический AST-анализ Python-кода

Перед исполнением любого Python-кода (патчи `new_block`, файлы `scripts/*.py`, хэндлеры `commands.yaml`, инлайн-тесты `tests:`) проводится статический разбор через модуль `ast`:

```python
import ast

def audit_ast(source_code: str, filename: str = "<probe>"):
    tree = ast.parse(source_code, filename=filename)
    for node in ast.walk(tree):
        # 1. Поиск динамического исполнения кода
        if isinstance(node, ast.Call):
            if isinstance(node.func, ast.Name) and node.func.id in ("eval", "exec", "compile", "__import__"):
                raise SecurityError(f"Prohibited dynamic evaluation '{node.func.id}' in {filename}")
            
            # 2. Небезопасный subprocess с shell=True
            if isinstance(node.func, ast.Attribute) and node.func.attr in ("Popen", "run", "call", "check_output"):
                for kw in node.keywords:
                    if kw.arg == "shell" and getattr(kw.value, "value", False) is True:
                        raise SecurityError(f"Prohibited subprocess shell=True in {filename}")
```

### Критерии блокировки при AST-анализе:
- Использование `eval()`, `exec()`, `compile()`, `__import__()`.
- Вызовы `subprocess` с `shell=True` (разрешены только безопасные списки аргументов `['cmd', 'arg1']`).
- Подозрительные обращения к файловой системе: открытие файлов по абсолютным путям (`open('/etc/...')`, `open('~/.ssh/...')`).
- Несанкционированная модификация системного окружения: `os.environ['LD_PRELOAD']`, `sys.path.insert` на произвольные пути вне мода.
- Скрытые сетевые соединения через `socket`, `urllib`, `requests`, `httpx` в фоновых хуках без объявления в манифесте.

## 3. Аудит bash-скриптов, хэндлеров и мониторов

Если мод содержит исполняемые скрипты в `scripts/`, `handlers/` или фоновые демоны `monitors:`:

1. **Запрет сетевой подгрузки кода:** Конструкции `curl ... | sh`, `wget -O- ... | bash`, `python3 -c "$(curl ...)"` запрещены безусловно.
2. **Защита от Command Injection:**
   - Переменные конфигурации `${config.<key>}` и пользовательские аргументы команд не должны вставляться напрямую в строку шелла.
   - Обязательно использование `shlex.quote()` для всех динамических подстановок.
3. **Права доступа к файлам:**
   - Файлы скриптов не должны иметь биты SUID/SGID (`chmod u-s,g-s`).
   - Исполняемые скрипты должны иметь права не выше `0755`.
4. **Секреты:**
   - В скриптах не должно быть жестко закодированных API-ключей, токенов или паролей.
   - Все секреты должны объявляться в `config.yaml` с `sensitive: true` и запрашиваться через безопасное хранилище `secrets.yaml`.

## 4. Симуляция коллизий с активными модами (Collision Simulation)

В рабочей среде Hermes активно функционирует обширный пул системных и кастомных модов. Сторонний мод обязан проверяться на отсутствие конфликтов перед применением:

1. **Виртуальная симуляция наложения и коллизий (Composite Collision Simulation):**
   - Для непримененных модов вызов команды `diff <mod_id>` не работает (она предназначена для сравнения уже наложенных изменений ядра с чистым апстримом).
   - Для проверки совместимости патчей запускай валидацию с флагом строгой структуры:
     ```bash
     python3 ~/.hermes/mods/runner.py validate --strict-layout
     ```
   - Встроенный метод `simulate_composite_apply` класса `ModValidator`:
     * Создает виртуальную RAM-файловую систему на базе чистого апстрим-кода ядра Hermes.
     * Последовательно накладывает блоки таргетов всех активных и проверяемых модов в топологическом порядке графа зависимостей (DAG).
     * Обнаруживает коллизии: если `old_block` нового мода не найден в виртуальной памяти (участок уже изменен другим модом) или найден неоднозначно (>1 совпадений), регистрирует конфликт таргетов с указанием конфликтующих модов.
     * Выполняет `ast.parse()` на результирующем композитном коде каждого измененного Python-файла, блокируя наложение при возникновении синтаксических ошибок в композитном рантайме.
2. **Коллизии слэш-команд (Command Name Collisions):**
   - Проверь реестр команд:
     ```bash
     python3 ~/.hermes/mods/runner.py commands
     ```
   - Новый мод не должен переопределять существующие системные команды или команды других модов (если явно не указано `mode: replace`).
3. **Коллизии MCP-серверов:**
   - Идентификаторы MCP-серверов в секции `mcp_servers` должны быть глобально уникальными.
4. **Проверка графа зависимостей (DAG):**
   - Движок строит топологическую сортировку всех модов. Новый мод не должен создавать циклических зависимостей (например, A -> B -> A).

## 5. Пошаговый регламент безопасной установки

При поступлении стороннего мода следуй строгому регламенту:

### Шаг 1: Безопасный нативный импорт или изоляция в `$TMPDIR`
- **Для архивов (`.tar.gz`):**
  Категорически запрещено использовать ручную распаковку `tar` в общесистемном каталоге `/tmp`!
  Используй нативную команду безопасного импорта движка:
  ```bash
  python3 ~/.hermes/mods/runner.py import <archive.tar.gz>
  ```
  Команда `import` на базе `ModImporter`:
  - Обладает встроенной защитой от TarBomb и Path Traversal (проверка `is_relative_to(mods_dir)`).
  - Фильтрует опасные и кэш-файлы (`.git`, `__pycache__`, `secrets.yaml`, `.lock`, скрытые директории).
  - Безопасно извлекает файлы непосредственно в директорию модов без засорения системного диска.
  - Автоматически запускает валидацию манифестов через `ModValidator`.
- **Для сырых каталогов и исходников:**
  Если мод поступил в виде папки с исходным кодом, размещай временные файлы строго в изолированной песочнице `$TMPDIR` (`~/.hermes/cache/scratch/mod-audit`), запрещая использование системного `/tmp`:
  ```bash
  AUDIT_DIR="${TMPDIR:-/root/.hermes/cache/scratch}/mod-audit"
  mkdir -p "$AUDIT_DIR"
  ```

### Шаг 2: Проверка файлов, Strict Layout и симуляция наложения
```bash
python3 ~/.hermes/mods/runner.py validate --strict-layout
```
Убедись, что мод соблюдает разделение файлов (`mod.yaml`, `targets/*.yaml`, `config.yaml`, `commands.yaml`, `tests/`, `i18n/`), не содержит бинарников и скрытых файлов, а виртуальная симуляция наложения (`simulate_composite_apply`) возвращает `100% PASS` без конфликтов и ошибок синтаксиса AST.

### Шаг 3: Проверка на Path Traversal и статический аудит кода
Выполни статический AST-анализ Python-кода и проверку скриптов:
- Убедись, что все пути в `targets:` относительны и указывают строго внутрь ядра Hermes.
- Проверь скрипты и хэндлеры на отсутствие сетевой подгрузки кода (`curl | sh`), вызовов `eval`/`exec`, небезопасного шелла (`shell=True`) и хардкода секретов.

### Шаг 4: Изолированный прогон тестов
Запусти тесты нового мода в обход кэша:
```bash
python3 ~/.hermes/mods/runner.py test <mod_id> --no-cache
```

### Шаг 5: Предстартовая верификация статуса
```bash
python3 ~/.hermes/mods/runner.py verify <mod_id> --no-cache
```
Убедись, что мод виден в системе и готов к наложению (`not_applied`).

### Шаг 6: Наложение со сторожевым таймером шлюза (Zero Downtime)
Примени проверенный мод:
```bash
python3 ~/.hermes/mods/runner.py apply <mod_id> --watchdog --watchdog-window 30
```
- **Автоматический сторож (Watchdog):** В течение 30 секунд контролирует процесс `hermes-gateway.service`. При падении или рестарт-лупе автоматически откатывает ядро к предпусковому дельта-снапшоту.
- **Строгий запрет рестартов:** Никаких ручных `systemctl restart hermes-gateway` — ядро подхватывает изменения на лету без простоя.
- **Подтверждение:** `python3 ~/.hermes/mods/runner.py verify <mod_id>` (должно вернуть `already_applied` с `verified: true`).
